# API задач

Реализованы создание, чтение владельцем, частичное редактирование, ручное подтверждение и публикация карточки. Базовый URL при запуске через Docker: `http://localhost:3000/api`.

## Доступ в локальном MVP

В Compose включён `DEMO_AUTH_ENABLED=true`. Передавайте заголовок `X-User-Id` с UUID существующего бизнес-пользователя. После `npm run db:seed` можно использовать `00000000-0000-4000-8000-010000000001`.

Это переключатель демонстрационной личности, **не настоящая аутентификация**: любой знающий UUID может выбрать этого пользователя. Для публичного сервера нужен отдельный механизм сессий или токенов. При `NODE_ENV=production` демо-доступ выключен независимо от переменной; без настроенного доступа методы задач возвращают `503 AUTH_NOT_CONFIGURED`. При локальном запуске Node вне Compose переменную нужно включить явно.

Сервер проверяет существование пользователя, роль `business` и владельца задачи. `owner_id` и `confirmed_by` берутся из выбранной сервером личности; их нельзя передать в теле запроса.

## Контракт

| Метод | Путь | Тело | Успех |
|---|---|---|---|
| POST | `/tasks` | `original_description` и необязательные поля карточки | 201 |
| GET | `/tasks/:id` | — | 200 |
| PATCH | `/tasks/:id` | `expected_version` и хотя бы одно изменяемое поле | 200 |
| POST | `/tasks/:id/confirm` | Только `expected_version` | 201 для новой версии, 200 для повторного подтверждения той же карточки |

Все ответы имеют форму:

```json
{
  "task": {
    "id": "UUID",
    "owner_id": "UUID",
    "original_description": "Нужен учёт заявок",
    "title": "Учёт заявок",
    "version": 2,
    "published_revision_id": null,
    "published_at": null
  },
  "confirmation": null,
  "has_unconfirmed_changes": true
}
```

Объект `task` в реальном ответе также содержит все поля карточки и даты создания/изменения. `confirmation` — последнее подтверждение, либо `null`. После подтверждения он содержит `id`, `task_id`, `confirmed_by`, `confirmed_at`, неизменяемый снимок `card`, `score`, `breakdown`, `readiness_level` и `missing`.

`has_unconfirmed_changes` сравнивает текущие поля карточки с последним подтверждением; если подтверждений нет, возвращает `true`. Исходное описание не входит в снимок карточки, поэтому его отдельное изменение не меняет этот флаг. Изменения карточки не меняют баллы предыдущего подтверждения.

## Поля запроса

Создание требует непустого `original_description`. При редактировании его нельзя очистить. Все значения — строки; строки обрезаются по краям. `null`, массивы, числа, нулевые символы и неизвестные поля отклоняются.

Поля карточки:

- `title`: название, до 300 символов; обязательно при подтверждении.
- `industry`: тема/отрасль, до 200 символов.
- `context`, `need`: контекст и потребность.
- `users_description`: пользователи решения.
- `data_materials`: доступные данные и материалы.
- `constraints_description`: ограничения.
- `expected_result`: ожидаемый результат.
- `success_criteria`: критерии успеха.
- `contact`: контакт, до 1000 символов.
- `interaction_format`, `feedback_process`: формат взаимодействия и обратной связи.

Остальные строки, включая исходное описание, ограничены 10 000 символами каждая. Весь JSON-запрос — 256 КБ. Для очистки необязательного поля передайте пустую строку. Пропущенные поля PATCH остаются прежними.

Передавайте `expected_version`, полученный из `task.version`. Каждое сохранение увеличивает версию. Если другая вкладка уже сохранила задачу, сервер вернёт `409 VERSION_CONFLICT`. Загрузите актуальную задачу и дайте пользователю сверить изменения; не повторяйте старое сохранение автоматически с новой версией.

Подтверждение принимает только номер версии: карточка и рейтинг берутся из БД. Оно блокирует строку на время транзакции, проверяет владельца и версию, сохраняет снимок и рассчитывает рейтинг по формуле БД. Повторное подтверждение неизменившейся карточки возвращает предыдущий снимок, в том числе при одновременных запросах.

Подтверждение **не публикует** задачу и не переключает ранее опубликованную версию. Для публикации используйте отдельный метод `POST /tasks/:id/publish`. Карточку с одним названием и нулевым рейтингом подтвердить можно.

## Пример для фронтенда

```js
const headers = {
  'Content-Type': 'application/json',
  'X-User-Id': '00000000-0000-4000-8000-010000000001',
};
async function api(path, method = 'GET', body) {
  const response = await fetch(`http://localhost:3000/api${path}`, {
    method, headers,
    ...(body === undefined ? {} : { body: JSON.stringify(body) }),
  });
  const result = await response.json();
  if (!response.ok) throw result.error;
  return result;
}

const created = await api('/tasks', 'POST', {
  original_description: 'Заявки теряются в переписке, нужен учёт.',
});
const edited = await api(`/tasks/${created.task.id}`, 'PATCH', {
  expected_version: created.task.version,
  title: 'Учёт заявок',
  context: 'Заявки поступают в мессенджер.',
  need: 'Собирать все заявки в одном месте.',
});
const confirmed = await api(`/tasks/${edited.task.id}/confirm`, 'POST', {
  expected_version: edited.task.version,
});
console.log(confirmed.confirmation.score); // 20
```

## Ошибки

Общий формат: `{"error":{"code":"VALIDATION_ERROR","message":"Проверьте поля запроса.","details":{"title":"..."}}}`. `details` присутствует, когда есть уточнения.

| HTTP | Причина |
|---|---|
| 400 | Ошибочный UUID/JSON, неподдерживаемые поля, типы, пустое описание или название при подтверждении |
| 401 | Отсутствующий, неверный или неизвестный X-User-Id |
| 403 | Пользователь не бизнес или не владелец задачи |
| 404 | Задача или маршрут не найдены |
| 409 | Версия задачи устарела; `details.current_version` содержит актуальную версию |
| 413 | Слишком большой запрос |
| 500 | Внутренняя ошибка; SQL и детали подключения клиенту не возвращаются |
| 503 | Демо-доступ выключен и авторизация ещё не настроена |

## Проверки

```sh
docker compose run --rm --no-deps backend npm run db:migrate
docker compose run --rm --no-deps backend npm run test:api
docker compose up -d backend
```

HTTP-тест поднимает сервер на случайном порту, создаёт отдельную схему PostgreSQL, применяет миграции и удаляет тестовую схему после проверки. Демоданные проекта не затрагиваются. Пользователю БД нужно право CREATE SCHEMA. Покрыты полный цикл, валидация, ограничения доступа, конфликты версий, параллельные запросы и сохранение опубликованного снимка.

## Открытый каталог с пагинацией

`GET /api/tasks?page=1&industry=Торговля&readiness_level=working`

Доступен без `X-User-Id`, в том числе при выключенном демо-доступе. Возвращает только опубликованные снимки карточек. `GET /api/tasks/:id` по-прежнему предназначен для владельца и возвращает его рабочую копию.

- `page`: целое число от 1 до 1000000, по умолчанию 1.
- `industry`: точная тема, до 200 символов; пустая строка отключает фильтр.
- `readiness_level`: `draft`, `working`, `ready`, `priority`; пустая строка отключает фильтр.
- Размер страницы фиксирован: **12**. Параметр изменения размера не поддерживается.
- Порядок: рейтинг по убыванию, дата публикации по убыванию, UUID по возрастанию для стабильного порядка при совпадениях.
- Если запрошенная страница больше последней, возвращается последняя доступная. Для пустого результата `page=1`, `total_pages=0`.

Ответ содержит `items`, `page`, `page_size`, `total`, `total_pages`, `filters` и `industries`. `total` учитывает фильтры, а `industries` содержит все непустые темы опубликованных задач для выпадающего списка. Каждый элемент содержит `id`, `card`, `industry`, `published_at`, `score`, `readiness_level`, `breakdown`, `missing`. Исходный черновик и неопубликованные изменения не возвращаются. Счётчик и страница читаются одним SQL-запросом из одного снимка данных.

Низкий рейтинг, включая 0, не скрывает опубликованную задачу. Публикация новых карточек выполняется отдельным методом `POST /tasks/:id/publish`. Демонстрационный seed содержит пять опубликованных задач.

Проверка `npm run test:api` включает отдельную схему с 25 опубликованными задачами и одной подтверждённой, но неопубликованной: страницы 12/12/1, фильтры, стабильный порядок, отсутствие утечки черновиков, пустой результат и валидация query-параметров.

### Публичная карточка

`GET /api/tasks/:id/published` без авторизации возвращает `{ "task": ... }` с опубликованной версией, полями карточки и рейтингом. Для неопубликованной или отсутствующей задачи — `404`, для неверного UUID — `400`. Рабочий черновик и последующие неподтверждённые изменения недоступны через этот метод.


## Публикация и обновление опубликованной версии

`POST /api/tasks/:id/publish`

Заголовки: `Content-Type: application/json` и `X-User-Id` владельца (локальный демо-доступ).

```json
{
  "expected_version": 2
}
```

Передавайте актуальный `task.version`, полученный после сохранения/подтверждения. Другие поля, включая ID снимка и рейтинг, не принимаются: сервер сам выбирает последнее подтверждение.

Успех: **200** с обычным ответом `{ task, confirmation, has_unconfirmed_changes }`. В `task` заполнены `published_revision_id` и `published_at`. При новой публикации или смене опубликованного снимка версия задачи увеличивается на 1, дата публикации обновляется. Используйте возвращённую версию для следующих действий. Повторная публикация того же снимка с актуальной версией возвращает 200 без изменения даты и версии. Повтор со старым `expected_version` возвращает 409, как и другие операции с версионной проверкой.

Правила:

- Только бизнес-пользователь — владелец задачи может публиковать её.
- Карточка должна быть подтверждена; текущие поля карточки должны совпадать с последним подтверждением.
- Рейтинг 0 разрешён. Все опубликованные задачи доступны в каталоге.
- Сохранение или подтверждение новой карточки не меняет текущую публикацию. Для обновления каталога нужно снова вызвать `/publish`.
- Проверки и обновление выполняются в транзакции с блокировкой строки задачи. История подтверждённых снимков сохраняется.
- Исходное свободное описание не входит в опубликованную карточку; его изменение само по себе не требует нового подтверждения карточки.

Ошибки: `400` — неверные поля/UUID/версия; `401` — нет демо-пользователя; `403` — чужая задача или роль; `404` — задача не существует. Бизнес-конфликты возвращают `409` с кодом:

| Код | Действие клиента |
|---|---|
| `VERSION_CONFLICT` | Загрузить актуальную задачу и сверить изменения |
| `CONFIRMATION_REQUIRED` | Подтвердить карточку перед публикацией |
| `UNCONFIRMED_CHANGES` | Подтвердить сохранённые изменения перед публикацией |

На странице редактирования подключены кнопки «Опубликовать» и «Обновить публикацию». Запрос выполняется через Vuex, новая версия задачи из ответа сохраняется в store.
