# Данные PostgreSQL

Миграции создают основу хранения для сценария «черновик → подтверждение → публикация → отклик → решение бизнеса». Создание, чтение владельцем, редактирование, подтверждение и публикация уже доступны через HTTP: [контракт API](../API.md). `/api/health` проверяет соединение с БД. API публикации реализован; API откликов и ручного выбора команды реализован.

## Запуск

Из корня проекта:

```sh
docker compose up --build -d
# Демонстрационные данные загружаются отдельно, только по явной команде:
docker compose exec backend npm run db:seed
docker compose exec backend npm run db:seed:catalog
docker compose exec backend npm run test:db
docker compose exec backend npm run test:api
```

При первом запуске с устаревшим volume backend может завершиться из-за отсутствия `pg`. В этом случае выполните `docker compose run --rm --no-deps backend npm ci`, затем `docker compose up -d backend frontend`.

Миграции выполняются при старте backend до сервера. Повторный запуск пропускает применённые файлы, сверяя контрольную сумму. Применённые миграции не редактировать: добавлять следующий SQL-файл. Каждая миграция выполняется в транзакции; advisory lock защищает от одновременного запуска.

Для запуска Node-команд без Docker задайте `DATABASE_URL` в окружении. Значение для стандартной локальной конфигурации: `postgresql://kazast:kazast_local@localhost:5433/kazast_ai`. Скрипты сами `.env` не читают. PostgreSQL доступен с хоста только через loopback, порт 5433. Пароли с символами URI нужно кодировать в URL подключения. Значения по умолчанию предназначены только для локальной разработки.

## Сущности

- `users`: демонстрационные пользователи с ролями business/student, без паролей и регистрации.
- `teams`, `team_members`: команды, навыки, интересы, технологии и состав.
- `tasks`: исходное описание и редактируемые поля карточки, владелец, целочисленная `version`, ссылка на опубликованную версию и дата публикации. `industry` используется как тема каталога.
- `clarification_questions`: упорядоченные вопросы и ответы. AI-сервис проверяет набор из 3–8 вопросов с разными целевыми полями; ответы можно сохранять частично.
- `task_revisions`: неизменяемые снимки карточки, подтверждающий владелец, дата и вычисленный рейтинг. JSON содержит строго строковые поля карточки. Пустая строка означает, что сведения ещё не предоставлены.
- `proposals`: идея, план, срок, необязательная HTTP(S)-ссылка на прототип, команда и ручное решение. Отсутствие прототипа не мешает раннему отклику; это допущение MVP. Нет ограничения количества откликов, в том числе повторных от одной команды.
- `progress_milestones`: минимальная запись фактического прогресса. Положительные баллы возможны только после подтверждения владельцем задачи для принятого отклика. Размер баллов в ТЗ не задан; окончательное правило определит будущий сервис.

Удаление связанных записей ограничено внешними ключами; каскадного удаления нет. API задач проверяет роль business и владельца. В локальном MVP личность выбирается через демо-заголовок; перед публичным запуском требуется полноценная авторизация. Поля `confirmed_by` и `decided_by` сервер должен брать из установленной личности, а не доверять телу запроса. Ограничения БД проверяют соответствие владельцу, но не заменяют авторизацию. API откликов проверяет принадлежность студента к команде по `team_members`.

## Подтверждение и публикация

Сохранение формы изменяет только `tasks` и увеличивает `version`. API проверяет `expected_version`, чтобы избежать перезаписи устаревшими данными. При ручном подтверждении сервис в транзакции блокирует строку задачи (`SELECT ... FOR UPDATE`) и создаёт `task_revisions`, копируя текущие поля карточки в `card`. Повторное подтверждение неизменившейся карточки возвращает уже созданный снимок. Генерация ИИ сама по себе не создаёт подтверждённую версию.

Метод `POST /api/tasks/:id/publish` проверяет владельца, `expected_version` и совпадение рабочей карточки с последним подтверждением. При первой публикации или смене снимка записываются `tasks.published_revision_id` и `published_at`, а `version` увеличивается. Повтор с актуальной версией и тем же опубликованным снимком не меняет дату или версию. Повтор со старой версией получает `409 VERSION_CONFLICT`. Внешний ключ запрещает ссылку на версию другой задачи. Для обновления опубликованной карточки нужно новое подтверждение и переключение ссылки на новую версию. Черновые правки не меняют каталог или его рейтинг. Название обязательно при подтверждении, прочие поля могут быть пустыми: даже рейтинг 0 не мешает публикации и откликам.

Статус публикации определяется наличием `published_revision_id`. Он независим от уровня готовности `draft`, который означает только рейтинг 0–39.

## Рейтинг

`readiness_breakdown(card)` возвращает баллы по всем семи критериям; `readiness_score(card)` — сумму. Веса: контекст + потребность 20, данные 20, результат 15, критерии успеха 15, ограничения 10, пользователи 10, связь с бизнесом 10. Для последнего критерия требуются контакт, формат взаимодействия и порядок обратной связи.

Группа получает полный вес, если все её поля непустые после удаления пробелов. Это проверка полноты подтверждённых сведений, не семантическая оценка качества. Оценка сохраняется вычисляемым столбцом: её нельзя передать от фронтенда или ИИ. Изменение шкалы потребует новой миграции и пересчёта сохранённых оценок.

`task_catalog` включает только опубликованные версии и возвращает рейтинг, расшифровку, список отсутствующих критериев и уровень: 0–39 draft, 40–69 working, 70–89 ready, 90–100 priority. Пример запроса каталога с фильтрами (NULL отключает фильтр):

```sql
SELECT * FROM task_catalog
WHERE ($1::text IS NULL OR industry = $1)
  AND ($2::text IS NULL OR readiness_level = $2)
ORDER BY score DESC, published_at DESC, id;
```

`team_progress` суммирует баллы подтверждённых этапов. Это отдельная шкала, не рейтинг бизнес-задачи.

## Демо и проверки

`npm run db:seed` создаёт 5 бизнес-пользователей, 5 студентов, 5 команд, 6 исходных описаний, 5 опубликованных карточек с рейтингами 20/55/70/90/100, по 3 вопроса к ним и 5 откликов. Все данные синтетические. Фиксированные UUID позволяют запускать seed повторно без дубликатов и без перезаписи пользовательских правок.

`npm run db:seed:catalog` добавляет 24 опубликованные карточки с рейтингами 20/40/55/70/90/100. Он пропускает уже существующие задачи целиком. На базе только этих двух наборов получается 29 опубликованных карточек; задачи, созданные через интерфейс, учитываются дополнительно.

`npm run test:api` создаёт отдельные тестовые схемы, применяет миграции и проверяет HTTP-сценарии создания, подтверждения, публикации, обновления и публичного просмотра. Проверка каталога использует 25 опубликованных задач для страниц 12/12/1. Тестовые схемы удаляются после завершения.

`npm run test:db` проверяет ограничения на реальном PostgreSQL. Тестовые записи создаются внутри транзакции и откатываются: публикация чужой версии, неизменяемость подтверждения, изоляция черновых правок, отклики при нулевом рейтинге, выбор нескольких команд, решения владельца и подтверждение прогресса.

Данные Docker хранятся в volume `postgres_data` и сохраняются после остановки контейнеров. Команда `docker compose down -v` удалит volumes вместе с данными; для обычной остановки используйте `docker compose down`.


## Миграции и подключение бэкенда

PostgreSQL 16 запускается сервисом `db`. Backend использует Node.js-драйвер `pg` без ORM, общий пул `src/db/pool.js` и параметризованные SQL-запросы. `DATABASE_URL` внутри Compose указывает на `db:5432`; URL в `.env.example` предназначен для Node-команд, запущенных на хосте.

| Файл / таблица | Назначение |
|---|---|
| `001_initial.sql` | Основные сущности, связи, ограничения, функции рейтинга, триггеры и представления |
| `002_task_version.sql` | Поле `tasks.version` и увеличение версии при UPDATE |
| `schema_migrations` | Создаётся runner-скриптом; хранит имя, SHA-256 и дату применения файла |

Runner `scripts/migrate.js` удерживает advisory lock на время запуска, проверяет контрольные суммы и применяет каждый новый файл в отдельной транзакции. Изменение уже применённого файла приводит к ошибке. Для ручного запуска: `docker compose exec backend npm run db:migrate`.

## Связи и границы ответственности

- `users → tasks`: один владелец может иметь много задач.
- `users ↔ teams`: состав команды хранится в `team_members`.
- `tasks → clarification_questions` и `tasks → task_revisions`: вопросы и история подтверждений принадлежат задаче.
- `tasks.published_revision_id → task_revisions`: составной внешний ключ учитывает ID задачи и запрещает публикацию чужого снимка.
- `tasks + teams → proposals`: любое число откликов; несколько откликов могут иметь статус `accepted`.
- `proposals → progress_milestones`: этап относится к предложению команды.

Триггеры запрещают изменение подтверждённых снимков, проверяют владельца подтверждения/решения и условия начисления баллов. Они не устанавливают личность вызывающего пользователя: это ответственность API. В текущем MVP API задач использует локальный демо-доступ, API откликов проверяет роль студента и членство в команде, а API прогресса ещё нет.

`task_catalog` и `team_progress` — обычные SQL-представления, не отдельные копии данных. После переключения опубликованного снимка каталог сразу читает новую карточку и её рейтинг. Публичный API каталога считает страницы и выбирает карточки в одном SQL-запросе; размер страницы — 12. Редактируемые поля `tasks` не попадают в публичный ответ.

API решений допускает переход из `pending` в `accepted` или `rejected`, повтор того же решения не меняет дату. Изменение уже принятого решения в MVP запрещено на уровне сервиса. Ограничения БД по-прежнему допускают несколько принятых предложений по одной задаче.

Список «Мои задачи» (`GET /api/tasks/mine`) выбирает `tasks` по `owner_id`, соединяет последний подтверждённый и опубликованный снимки `task_revisions`, считает отклики и ожидающие решения из `proposals`. Пагинация по 12 и фильтрация выполняются в PostgreSQL. Новых таблиц и миграций для этого списка не требуется.

### Уточнение с AI

Миграция `003_clarification_sessions.sql` добавляет раунды `clarification_sessions` (задача, версия, режим local/openai, предложенная карточка, дата). В `clarification_questions` добавлены `session_id` и `field`; позиция уникальна внутри раунда. Старые вопросы без раунда сохраняются. Новые вопросы не удаляют предыдущие ответы. Изменение ответов сбрасывает предложение карточки. Запись раунда, ответов и предложения сериализуется блокировкой задачи и проверкой её версии. Предложение не является подтверждённым снимком `task_revisions`.
